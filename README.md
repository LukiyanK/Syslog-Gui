# Syslog-Gui

Веб-приложение на **Python**: приём сетевых логов в стиле syslog по **UDP** или **TCP**, настройка порта и протокола через **браузер**, просмотр сообщений **в реальном времени**, опциональная запись в файл, выгрузка и очистка буфера.

Стек: **asyncio** (приёмник), **Starlette** (HTTP/WebSocket), **uvicorn** (ASGI-сервер). Отдельные файлы фронтенда — статический `static/index.html` с ванильным JavaScript.

## Назначение

- Запустить на машине простой **слушатель** на выбранном порту, принимающий **сырой текст** по UDP (датаграммы) или по TCP (строки, разделённые переводом строки).
- Управлять **портом** и **протоколом** без правки кода и перезапуска вручную (параметры применяются через API; при смене порта/протокола приёмник пересоздаётся).
- Смотреть входящие сообщения в браузере с минимальной задержкой (**WebSocket**).
- По желанию **дописывать** сообщения в файл на диске и **скачивать** накопленный буфер в памяти как `.txt` или JSON.

Это **не** полная реализация RFC 5424/3164: парсинга приоритетов и facility нет — сохраняется текст и метаданные «кто и когда прислал».

## Как это устроено

### Точка входа

`run.py` поднимает **uvicorn** с приложением `app.main:app` на `WEB_HOST` / `WEB_PORT` (по умолчанию `0.0.0.0:8080`).

### Жизненный цикл приложения (lifespan)

При старте Starlette:

1. Читается конфиг из `DATA_DIR` / `CONFIG_FILE` (`config.json`).
2. Вызывается `SyslogReceiver.start(config)` — останавливается предыдущий сокет (если был) и поднимается либо UDP, либо TCP в соответствии с настройками.

При остановке процесса приёмник корректно закрывается.

### Приёмник syslog (`app/syslog_server.py`)

Класс **`SyslogReceiver`**:

- **UDP**: `asyncio` + `DatagramProtocol` — на каждую датаграмму создаётся задача `append(...)`.
- **TCP**: `asyncio.start_server` — на каждое соединение читаются строки через `readline()`; каждая строка — отдельное сообщение.
- Слушает на `0.0.0.0` и выбранном **порту** из конфигурации.
- Внутри хранит **кольцевой буфер** последних сообщений в памяти (до **2000** записей; старые вытесняются).

Каждое сообщение — объект **`LogEntry`**:

| Поле | Смысл |
|------|--------|
| `received_at` | Время приёма в UTC (ISO 8601) |
| `remote` | Адрес отправителя, например `192.168.1.10:54321` |
| `protocol` | `udp` или `tcp` |
| `message` | Текст (UTF-8 с заменой ошибочных байтов) |

Если включена запись в файл (`persist_to_file`), для каждой записи в отдельном потоке (`asyncio.to_thread`) выполняется **дозапись** строки в выбранный файл. Формат задаётся полем **`persist_format`**:

- **`txt`** — одна строка на сообщение: `время<TAB>PROTOCOL<TAB>remote<TAB>message` + перевод строки.
- **`json`** — **JSON Lines**: одна строка = один JSON-объект с полями `received_at`, `remote`, `protocol`, `message` (удобно для потоковой обработки).

### Веб-слой (`app/main.py`)

- **`GET /`** — отдаёт `static/index.html`.
- **`/static/...`** — статика.
- **REST** для конфигурации и сообщений (см. ниже).
- **`WS /ws/logs`** — подписка на события в реальном времени.

## Поток данных

```
[Клиенты по сети] --UDP/TCP--> SyslogReceiver.append()
                                    |
                    +---------------+---------------+
                    |               |               |
               deque буфер    (опционально)    WebSocket broadcast
               (до 2000)      файл на диске    всем подключённым UI
```

1. Датаграмма или строка TCP попадает в `append`.
2. Запись добавляется в буфер под блокировкой.
3. При необходимости строка дописывается в файл.
4. Всем подключённым WebSocket-клиентам отправляется JSON с новым сообщением.

## Конфигурация и хранение

Файл **`DATA_DIR/CONFIG_FILE`** (по умолчанию `./data/config.json`) — JSON с полями:

| Поле | Тип | Описание |
|------|-----|----------|
| `listen_port` | число | Порт приёмника (1–65535), по умолчанию **5514** |
| `listen_protocol` | строка | `"udp"` или `"tcp"` |
| `persist_to_file` | bool | Писать ли каждое сообщение в файл |
| `persist_format` | строка | `"txt"` или `"json"` (формат строк при записи на диск) |
| `messages_file_path` | строка | Путь к файлу; см. ниже |

**Путь к файлу логов** (`messages_file_path`):

- **Пустая строка** — используется `DATA_DIR/logs/syslog.log` при `persist_format: "txt"` или `DATA_DIR/logs/syslog.jsonl` при `"json"`.
- **Относительный путь** — относительно `DATA_DIR` (например `logs/app.log`).
- **Абсолютный путь** — как указано в системе.

Порт **5514** выбран по умолчанию как непривилегированный; стандартный syslog **514** на Unix часто требует запуска от **root** или capabilities (`CAP_NET_BIND_SERVICE`).

## Веб-интерфейс

Одна страница `static/index.html`:

- Поля **порт** и **протокол** — при изменении отправляется `POST /api/config` (автосохранение).
- **Запись в файл** — чекбокс, **формат** (текст или JSON Lines) и путь; при выключенном чекбоксе поля неактивны; запись на диск не выполняется.
- Блок **«Сообщения»** подключается к **`/ws/logs`** и отображает поток; при первом подключении приходит история из буфера.
- Кнопки **Скачать .txt / JSON** — запрос к `GET /api/messages/export`.
- **Очистить** — `POST /api/messages/clear` с подтверждением; очищается только **память**, файл на диске не обрезается.

---

## HTTP API

| Метод и путь | Назначение |
|--------------|------------|
| `GET /api/config` | Текущий JSON конфигурации |
| `POST /api/config` | Применить конфиг; тело — JSON с полями как в `config.json` (обязательны `listen_port`, `listen_protocol`) |
| `GET /api/messages?limit=N` | Последние N сообщений из буфера (N от 1 до 1000, по умолчанию 200) |
| `GET /api/messages/export?format=txt` | Скачать весь буфер как текст (табуляции, как при записи в файл) |
| `GET /api/messages/export?format=json` | Скачать весь буфер как JSON-массив объектов `LogEntry` |
| `POST /api/messages/clear` | Очистить буфер в памяти; ответ `{"ok": true, "cleared": true}` |

Ошибки валидации или занятого порта возвращаются как JSON `{"detail": "..."}` со статусом 4xx.

## WebSocket

**URL:** `ws://<хост>:<WEB_PORT>/ws/logs` (при HTTPS — `wss://`).

Сообщения — текстовые фреймы с одним JSON на фрейм.

| `type` | Смысл |
|--------|--------|
| `history` | `{ "type": "history", "entries": [ {...}, ... ] }` — до 500 последних записей при подключении |
| `message` | `{ "type": "message", "entry": { "received_at", "remote", "protocol", "message" } }` |
| `cleared` | `{ "type": "cleared" }` — буфер очищен через API |

Клиент может слать любые входящие кадры (например пинги); они игнорируются, соединение держится открытым.

## Запуск

```bash
python3 -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python run.py
```

Интерфейс: [http://localhost:8080](http://localhost:8080) (если `WEB_HOST`/`WEB_PORT` не меняли).

Параллельно процесс слушает **отдельный порт** для syslog (по умолчанию **5514**) — убедитесь, что он свободен и не блокируется файрволом.

## Проверка отправкой тестового сообщения

После запуска, с учётом выбранного в UI порта и протокола:

**UDP (пример для macOS/Linux):**

```bash
echo "test udp" | nc -u -w1 127.0.0.1 5514
```

**TCP** (в UI должен быть выбран TCP):

```bash
echo "test tcp" | nc -w1 127.0.0.1 5514
```

На **GNU/Linux** для UDP иногда удобно `logger` (если доступен с нужными опциями):

```bash
logger --server 127.0.0.1 --port 5514 --udp "hello"
```

## Ограничения и примечания

- Один активный протокол приёма (**либо** UDP, **либо** TCP); переключение закрывает старый сокет и открывает новый.
- Буфер только в **RAM**; при перезапуске процесса история из памяти теряется (файл на диске при включённой записи сохраняется).
- Парсинг syslog-формата не выполняется: то, что пришло по сети как полезная нагрузка, отображается как текст.
- Для портов &lt; 1024 на Unix может потребоваться повышение привилегий или настройка capabilities.
